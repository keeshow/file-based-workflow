# AGENTS.md — Agent 项目协作规范

> 适用范围：本仓库。本文仅规定通用 Agent 开发工作流；项目专属约束统一放在 `docs/project-rules.md`。

## 1. 基本原则

- 以用户明确需求为任务边界；Agent 自主分析、规划、执行和维护文档，不擅自扩展功能。
- 遵循现有架构、编码规范和约定；以最小必要变更完成任务，避免无关重构。
- 基于实际代码、Git 状态和验证结果作出判断；历史文档仅作参考，发现冲突先核实。
- 区分已验证事实、合理推测与待验证事项；不得虚构执行、测试或完成结果。
- 按需读取文档、按价值更新文档，不为满足流程而创建冗余文件。
- 开发与验证必须遵守适用的项目专属约束；具体规则加载与冲突处理见第 10 节。

## 2. 文档结构与职责

```text
project/
├── AGENTS.md            # Agent 规则（本文件）
├── handoff.md           # 当前项目状态和交接快照
├── handoff.md.example   # Handoff 写法示例（可选）
├── docs/
│   ├── README.md        # 文档导航索引
│   ├── project-rules.md # 项目专属约束（可选）
│   ├── tasks/           # 独立、可验收的阶段任务；可含 00-task.md.example
│   ├── notes/           # 排查记录与专题笔记；可含对应 .example 写法示例
│   └── references/      # 原始手册、协议及外部资料
└── ...                  # 项目代码与配置
```

- `AGENTS.md`：可跨项目复用的 Agent 工作流与通用安全边界；不记录项目专属约束或日常进度。
- `docs/project-rules.md`：当前项目长期有效的工作范围、编码要求、架构边界和构建/验证权限；可不存在。
- `handoff.md`：当前阶段、已完成事项、进行中任务、阻塞、下一步及关联路径；不是流水账。
- `docs/tasks/`：任务目标、范围、约束、计划、验收标准及结果。
- `docs/notes/`：排查记录与专题笔记，分别保存关键排查过程和整理后的知识、研究、方案或经验；排查记录不以找到根因为创建前提。
- `docs/references/`：原始参考资料及来源、版本信息；分析结论写入 `notes/`。
- `docs/README.md`：重要文档链接与导航；不重复维护详细状态。
- `.example` 文件：撰写示例，首次创建或整理对应文档时按需参考；不属于实际项目状态、任务或验收证据，不纳入任务编号和状态统计。实际文档依据项目事实编写，不直接复制示例结论。

缺失的文档或目录仅在实际需要使用时创建；不要生成空白占位文档。

## 3. 新会话与任务接手

1. 遵循当前路径适用的 `AGENTS.md` 指令。
2. 在执行项目相关任务前，检查 `docs/project-rules.md`；存在则读取并遵守，缺失则按通用规范继续，不自动创建（详见第 10 节）。
3. 如存在 `handoff.md`，读取并识别当前状态和待办。
4. 根据用户任务定位相关代码、`docs/tasks/` 文档，必要时查阅 `docs/README.md`、`docs/notes/`、`docs/references/`；不要批量读取无关资料。
5. 检查相关文件及 Git 分支、工作区改动，确认文档信息未过时；保护现有未提交修改。
6. 明确任务目标、范围、约束、验收方法和可执行的下一步；关键信息不足且会影响范围或验收时再询问用户。

## 4. Task 规划与粒度

- **用户决定**：需求目标、功能边界、关键约束和验收要求。
- **Agent 决定**：技术实现细节、执行步骤、合理拆分与文档维护；不能自行追加未授权的开发目标。
- 一个 Task 对应一个相对独立、可验收的功能或阶段，不按日期、会话次数、单个命令或函数划分。
- 简单、一次性修改可不建 Task；跨阶段、跨会话、复杂或有明确交付物的工作应建立或维护 Task。
- 一个 Task 内按可检查的主要步骤管理实施进度，不按每轮对话、命令、函数或界面微调列项；仅在多个目标可独立验收时拆成多个 Task。
- 任务超大或目标不清晰时，提出分阶段方案；涉及扩大范围、改变关键方案或验收标准时先获用户确认。
- 文件命名：`docs/tasks/NNN-short-name.md`，编号唯一、稳定；优先维护已有相关文档。
- Task 维护当前任务安排与验收依据，建议内容为：**状态、目标、范围/非目标、主要步骤及完成情况、关键决策、验收标准及结果、遗留问题、下一步和关联资料**；约束按需记录，已有项目规则用链接引用。
- 实施步骤的勾选只表示该步骤完成；验收按约定标准分别记录结果。功能已实现但仍有必要验证时继续保持 `IN_PROGRESS`，不为结束 Task 而移走未解决的验收项。
- 状态：`TODO` / `IN_PROGRESS` / `BLOCKED` / `DONE`。`DONE` 必须满足已约定的验收标准；无法验证则明确标注待验证，不得假定通过。
- 初次撰写或整理 Task 时可参考 `docs/tasks/00-task.md.example`；章节按任务需要选用，不为套用示例补写无用内容。

## 5. 开发执行与验证

1. 修改前了解现有实现、影响范围及相关约束；复杂任务先提出计划，简单明确任务可直接实施。
2. 修改与目标直接相关的最小文件集；不随意变更公共接口、依赖版本、项目架构或关键配置。
3. 遇到异常先分析证据与根因，不盲目重复尝试；技术决策记录必要理由及影响。
4. 完成后在当前项目授权范围内执行适当的构建、测试、静态检查或运行验证；项目约束限制的操作不得自动执行。
5. 无法执行的测试必须说明原因和剩余风险；明确区分“已修改”“已构建”“已验证”“已验收”。

## 6. 文档自主维护

Agent 在**已授权任务范围内**自行判断并执行以下操作，不需要逐项征求许可：

- 创建/更新必要的 Task，记录实际进度、阻塞和验收证据。
- 重要故障需要持续排查、技术研究需要保留依据、形成可复用方案，或用户要求整理专题笔记时，创建/更新 `docs/notes/`。
- 当前状态或交接信息发生实质变化时更新 `handoff.md`。
- 新增、移动重要文档时维护 `docs/README.md` 索引。
- 修复确认过时的文档事实或失效链接。

维护要求：

- **事件驱动更新**：重要里程碑、状态变化、问题定位、方案确定、交接中断时更新；无需每次对话都更新全部文档。
- **单一事实来源**：需求拆解、实施进度和验收结论以 Task 为准；关键排查过程、方案和技术结论放 Note，Task 保留问题对验收的影响、剩余行动及链接；Handoff 只维护项目级摘要和入口。使用说明保留操作方法与限制，不另行维护相同进度或验收清单。
- **合并更新**：将新进展合并到对应步骤、验收项或问题中，替换失效状态和待办，不按日期或对话轮次追加流水账。已完成步骤简记结果；不能只在开头声明“以下为历史”而长期保留失效待办。仍影响判断的历史验证事实应保留，修复前失败、修复后通过分别注明版本、条件和结论；被推翻的结论注明原因，不再作为有效依据。
- **保留边界**：影响验收、解释关键决策、支持或反驳故障假设、避免重复无效尝试，或支撑未解决问题的信息应保留。仅重复既有结论且不增加有效条件或证据的过程可合并；命令、测试数量、哈希和逐轮打包经过只在影响判断或复现时记录，不要求保存每次操作。
- **验收证据**：按验收项记录关键结果、适用版本和条件、证据入口，以及未通过或未验证的部分；区分用户反馈、Agent 检查和实机结果。证据须说明保存位置和可获取性；临时、本机、未提交或被忽略的文件注明保存限制，不视为长期归档。重要结论的唯一依据应先保存必要内容；无法保存时标明证据缺口及需补做的验证，不假定可由 Git 恢复。不要求将全部原始日志纳入 Git。
- **故障记录**：重要、复杂或跨会话排查可在根因未明时维护 Note，记录现象、版本与复现条件、关键尝试及结果、已确认事实、已排除或尚待证实的假设、下一步，修复后补充措施和复测结论。排除假设须限定适用条件；未复现不等于已排除或已修复，离线检查不能替代实际运行验证。按问题和假设合并更新，不把逐轮操作流水转存到 Note；可参考 `docs/notes/debug-download-memory.md.example`。
- **精简与追溯**：整理旧文档前，先核对重要信息及证据的保留位置；有价值的排查和结论优先合并到已有 Note，独立主题再新建，无法判断价值的信息先保留待核实。普通修改经过由已提交的 Git 历史追溯，当前文档保留必要入口。用户明确要求完整保留过程时，另作可发现的归档并建立链接；不将完整归档设为每个 Task 的必需步骤。
- **信息准确**：尚未完成、未经测试、无法复现或存在风险的事项明确标记；不可将计划写成成果。
- 不创建重复文档；优先更新已有文档；不因少量变更强制生成笔记。

Note 分类与写法：

- **排查记录**：文件命名为 `debug-主题.md`，开头标明“类型：排查记录”及“排查中／已定位／已解决”等实际状态。服务于继续排查，按上述故障记录要求保留关键尝试、证据和判断变化；根因已定位但尚未修复或复测时，不标为已解决。参考 `docs/notes/debug-download-memory.md.example`。
- **专题笔记**：文件命名为 `note-主题.md`，开头标明“类型：专题笔记”，按需说明适用范围。服务于阅读和复用，按主题整理知识、方案、原理或经验，说明结论及其限制；依据来自排查时链接原记录，不重复展开过程。参考 `docs/notes/note-download-memory-validation.md.example`。
- 不要求同一问题生成两份文档。排查完成后在原记录补充结论；仅在用户要求独立总结或内容具有独立复用价值时另建专题笔记，不自动将排查记录改写为专题笔记。
- 按内容用途选择文档，不按请求中是否出现“总结”分类：任务进度更新 Task，项目当前状态更新 Handoff，知识与经验总结放专题笔记。

## 7. Handoff 状态与交接规范

### 7.1 定位与初始化

- `handoff.md` 是**项目当前状态快照**，用于跨会话、跨 Agent 恢复工作；不充当开发日志、完整 Task 清单或技术笔记。
- Agent 根据本节规范自主创建与维护 `handoff.md`，无需日常更新审批；初次撰写或整理时可参考 `handoff.md.example`，实际内容依据项目事实填写。
- 文件缺失时，先检查实际项目状态；存在进行中任务、阻塞或有价值的交接信息时创建。新建空项目且尚无实质状态时可暂不创建。
- 文件为空时视为尚未初始化，不将示例当作真实状态，也不为填满章节编造项目进度。
- 文件已存在时优先更新原文件；不得因格式调整丢失未核实的有效信息。

### 7.2 固定内容结构

`handoff.md` 依次包含以下章节；无内容时填写“无”，字段可按项目需要精简：

1. **项目概况**：项目目标、当前开发重点。
2. **当前阶段**：开发阶段、当前 Task 路径及状态；无 Task 时明确注明。
3. **最近完成**：近期关键成果与实际验证情况，不罗列完整历史。
4. **正在进行**：当前工作、已完成部分、尚未完成部分。
5. **问题与阻塞**：问题现象、影响、已确认结论及待验证事项；没有阻塞则填写“无”。
6. **下一步行动**：按优先级列出可直接执行的操作，注明必要前置条件或验证方式。
7. **关键上下文**：恢复任务必需的环境、约束、关键决策和注意事项。
8. **相关文档与代码**：关联 Task、Note、参考资料及关键文件的有效相对路径。

文件开头记录**最后更新时间**；时间无法可靠获取时不编造。避免复制 Task 中的需求全文、实施清单或 Note 中的完整排查过程。

各章节只保留接续工作所需的信息。同一 Task 的详细验收结果、测试清单和资源数据集中在对应文档，Handoff 写结论与链接；同一问题在不同章节分别说明影响或行动，不重复展开完整背景。

### 7.3 自主更新时机

以下事件发生后，应检查并在有实质变化时更新 `handoff.md`：

- 当前 Task 开始、切换、完成，或项目进入新阶段。
- 重要成果经验证，或原验证结论被推翻。
- 发现、解除影响后续开发的阻塞。
- 下一步行动、关键约束或继续开发所需路径发生变化。
- 用户要求暂停、交接，或工作即将因上下文切换而中断，且 Agent 有机会写入文档。

小范围改动且不影响交接状态时无需更新；不要求每轮对话重写。

### 7.4 状态维护与一致性

- 以**覆盖过时快照、保留仍有效信息**的方式维护，不按日期连续追加流水账。
- 已完成事项从“正在进行”移至“最近完成”，只保留影响后续工作的摘要；验收结论留在 Task，技术结论留在 Note，普通修改经过由 Git 追溯，不将完整历史转存到 Task。
- 阻塞解决后移除当前阻塞，并在相关 Task/Note 中保留必要结论。
- `handoff.md` 的 Task 状态、下一步行动须与相关 Task 文档一致；冲突时先核实代码、Git 和测试事实，再同步修正。
- 只记录实际完成的工作；未执行、未验证、推测及等待用户决策的事项必须明确标识。
- 不记录密钥、令牌、密码、敏感数据或不必要的大段日志。

### 7.5 新会话恢复检查

新 Agent 读取 `handoff.md` 后，应能明确：**当前做什么、已验证什么、卡在哪里、接下来做什么，以及从哪些文件继续**。

- 按“下一步行动”定位必要的 Task、代码及参考文档，核实工作区实际状态后再执行。
- 若快照缺失、陈旧或互相矛盾，先核查可用证据，必要时标记待核实；不得猜测完成情况。
- 若用户提出新的任务，以本次明确要求为准；不得仅凭旧 Handoff 自动开展未获授权的工作。

## 8. 审批边界与安全

**无需额外审批**：在现有授权范围内的常规代码修改、合理计划细分、测试及上述非破坏性文档维护（以运行环境实际授权为前提）。

**必须先获得用户确认**：

- 修改 `AGENTS.md` 的规范、权限或审批规则，或修改 `docs/project-rules.md` 中具有约束力的条款。
- 改变已确认的目标、需求范围、验收标准或关键架构决策。
- 执行超出任务范围的重大重构、引入有显著影响的新依赖或改变部署行为。
- 删除具有长期价值的文档、关键代码、用户数据或历史记录。
- 执行破坏性操作，或未经授权的 Git 提交、推送、合并、重置、清理及发布。

其他要求：

- 不覆盖或撤销用户及其他参与者的未提交修改；遇到冲突先说明。
- 不将密码、密钥、令牌或个人敏感信息写入文档、代码示例及日志。
- 遵守平台沙箱、工具权限及更高优先级指令；本文件不代表工具操作已获授权。
- 需审批但尚未获得确认时，可继续不受影响的分析或只读检查，不擅自实施受限变更。

## 9. 任务结束时的输出

简要报告：

1. 完成内容及主要改动文件。
2. 执行的验证及实际结果；未验证项和风险。
3. 当前任务状态、阻塞和建议的下一步。
4. 本次创建或更新的文档（如有）。

不以文档更新代替实现和验证；不生成无意义的总结。

## 10. 项目专属约束的加载与优先级

### 10.1 固定入口

- 项目专属约束统一存放在仓库根目录下的 `docs/project-rules.md`，不写入本文件。
- Agent 接手项目或开始项目相关任务时，检查该文件是否存在；存在则读取，并在后续执行中遵守适用条款。
- 文件不存在时视为未定义额外项目约束，按本文件及其他适用指令执行；不得因此创建空文件或猜测项目限制。
- 同一会话内，已读取且未变化的项目规则无需每轮重复读取；规则文件发生变化或上下文不可靠时重新检查。

### 10.2 规则分工与适用

- `AGENTS.md` 负责通用流程、文档职责、审批与安全边界；`docs/project-rules.md` 负责具体项目的工作范围、编码规范、架构约束和工具/构建/硬件操作限制。
- 项目规则可细化或收紧通用执行要求，但不得削弱通用安全、审批要求或上级指令。
- 通用规范建议执行、而项目规则禁止自动执行的操作，以项目限制为准。例如项目禁止自动编译时，只执行允许的检查并说明未编译。
- 遇到无法兼容的规则或用户指令与既有项目限制存在实质冲突时，先说明冲突并请求用户明确决定；不得自行绕过限制。
- `docs/project-rules.md` 属于需要用户把关的长期约束，Agent 可以提出修订建议，但未经用户确认不得自行改写其约束条款；普通 Task、Note、Handoff 的自主维护权限不延伸到此文件。

### 10.3 按需导航

- 项目规则如引用其他架构或参考文档，仅在当前任务涉及对应模块时按需阅读，不批量加载全部资料。
- 不把临时任务进度、Bug 过程或当前交接状态写入项目规则；分别使用 `docs/tasks/`、`docs/notes/` 和 `handoff.md`。
