# 文档维护细则

> 整理旧文档、合并进展或记录验收证据前阅读。维护原则见 `AGENTS.md` 第 6 节，本文说明具体做法。

## 单一事实来源

各类文档的分工见 `AGENTS.md` 第 6 节。补充说明：Task 保留问题对验收的影响、剩余行动及链接；专题笔记仅在明确授权后整理；使用说明保留操作方法与限制，不另行维护相同进度或验收清单。

## 写法要求

- 文档面向人阅读：一句话说一件事；多个事项用列表，多个对象的比较用表格。
- 不用“／”串联多个对象，改用顿号或分别列出。
- 版本、环境、样本等限定条件放在表格或证据表中，不全部堆进叙述句。
- 中文与英文、数字之间加空格；代码标识符、文件路径和命令用反引号标出。

## 合并更新

- 将新进展合并到对应步骤、验收项或问题中，替换失效状态和待办，不按日期或对话轮次追加流水账。
- 已完成步骤简记结果；不能只在开头声明“以下为历史”而长期保留失效待办。
- 仍影响判断的历史验证事实应保留，修复前失败、修复后通过分别注明版本、条件和结论；被推翻的结论注明原因，不再作为有效依据。

## 保留边界

- 影响验收、解释关键决策、支持或反驳故障假设、避免重复无效尝试，或支撑未解决问题的信息应保留。
- 仅重复既有结论且不增加有效条件或证据的过程可合并；命令、测试数量、哈希和逐轮打包经过只在影响判断或复现时记录，不要求保存每次操作。

## 验收证据

- 按验收项记录关键结果、适用版本和条件、证据入口，以及未通过或未验证的部分；区分用户反馈、Agent 检查和实机结果。
- 证据须说明保存位置和可获取性；`.agent-local/` 中的文件及其他临时、本机、未提交或被忽略的文件注明保存限制，不视为长期保存。
- 重要结论的唯一依据应先保存必要内容；无法保存时标明证据缺口及需补做的验证，不假定可由 Git 恢复。不要求将全部原始日志纳入 Git。

## 精简与追溯

- 整理旧文档前，先核对重要信息及证据的保留位置；历史资料优先维护原文和导航，另建摘要笔记须遵守 `AGENTS.md` 第 6 节的专题笔记授权规则。
- 排查信息优先合并到已有 Debug，独立排查主题再新建；无法判断价值的信息先保留待核实。
- 修改经过及整理前的原文由已提交的 Git 历史追溯，不另存副本；当前文档保留必要入口。
